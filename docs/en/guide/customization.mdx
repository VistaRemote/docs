# Customization: why VistaRemote

Teams pick VistaRemote for secondary development because **they can change it, they can hire for it, and the data stays on their network**. It is built for private deployments and industry-specific work, not for million-viewer live streams.

## Why customize this product

| Reason | What it means for your team |
| :--- | :--- |
| **One main language** | Signaling, the Web controller, admin, the Electron Agent, the phone app, and AI jobs are **TypeScript**. Hire Node and React engineers instead of a separate C++ remote-desktop team |
| **One contract** | Cross-platform types live in `shared`. Change the protocol there first so Web, desktop, and mobile do not invent their own fields |
| **Spec-driven** | Behavior is written in a Spec before code. People and AI collaborators change the same description, and review can check it |
| **Repos stay separate** | Electron, React Native, and NestJS do not share one install. Clone the repo you are changing. Rsbuild starts quickly |
| **Ops you already know** | **PostgreSQL + Docker**. One machine can run signaling, the database, recordings, and AI |
| **Heavy compute stays aside** | OCR and vision run in the Python worker under `ai`. The main path stays TypeScript |
| **Plugins, not only a full fork** | Industry rules, extra admin pages, and chat notifications can extend the product from a plugin manifest |

The languages are ordinary and the ecosystems are large. A small team can ship common enterprise changes in weeks:

- Corporate **SSO / OIDC**
- An **approval** step before a remote session
- Industry-specific **admin** fields and reports
- On-prem **OCR / vision** rules (data stays inside)
- Session events into WeCom, DingTalk, or your own tickets

## Compared with a closed client or a legacy C++ project

| | VistaRemote | Closed commercial remote desktop | Legacy C/C++ open source |
| :--- | :--- | :--- | :--- |
| Change the UI and admin | Edit React pages | Usually not possible | Often a native UI |
| Change the protocol | Edit `shared`, then build every client | Not possible | Bindings drift across languages |
| Hiring | Large TypeScript talent pool | Wait on the vendor | C++ desktop plus a private protocol |
| Where data lives | Your PostgreSQL, MinIO, and Ollama | Often the vendor cloud | However you deploy it |
| AI | A separate service, fully on your network | Often the vendor’s model | Usually none |

## Suggested order

```text
1. Read positioning and the module Spec you are changing
2. If the protocol changes, edit shared first
3. Change the server API or admin
4. Change the Web controller or Desktop Agent
5. Update docs for anything a user can see
```

## Who it fits

It fits **private networks, up to tens of thousands of sessions, teams who must own the data, and teams who will change the code**.

It does not fit a global live-streaming audience, or a purchase that requires a closed box and refuses self-hosting.
