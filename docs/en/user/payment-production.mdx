# Production payment readiness (ops)

Use this page to walk **mock → sandbox → production**. LuminaryWorks Entitlement already ships payment **adapters**; that is not live merchant enablement. Lite checkout (commerce **complete** / **status**, plus the Entitlement ingress webhook) can cache local `User.plan`. **WeChat Pay / Alipay merchant onboarding, notify DNS, and production PSP secrets are owner-ops — configured in your environment / Entitlement.** Product outbox delivery may still be in progress. Never commit merchant secrets.

Architecture: [Commercial billing](/architecture/commercial-billing). Admin modules: [Admin console](/user/admin-console). Spec: `spec/billing-commerce-spec.md`.

## Membership vs wallet

VistaRemote has **no** prepaid wallet, balance, or top-up SKU. Buyers purchase **Pro / Ultra subscription offerings** (Client `/membership` → commerce BFF → Entitlement).

Sandbox path:

1. Sign in once with unified OIDC so `users.logtoSub` is set (commerce `X-Act-As-Subject` is the Logto `sub`, not the local User UUID)
2. Non-production Entitlement with `PAYMENT_CONFIG_MASTER_KEY` can auto-seed a **mock** payment config; or enable mock/alipay sandbox in Admin
3. Membership: pick SKU → payment method (mock preferred) → **Complete payment**; mock captures on complete and syncs local `User.plan`
4. Live WeChat/Alipay merchant onboarding remains Entitlement owner-ops; this product does not ship a cross-product wallet

## Path: mock → sandbox → production

| Stage | Typical config | Behavior |
| :--- | :--- | :--- |
| **Mock (local)** | `ENTITLEMENT_MODE=off` | Local orders and plans. The order owner may call `POST /api/v1/billing/orders/:id/simulate-paid` (Controller JWT). Admin **Orders** **Simulate paid** calls `POST /api/v1/admin/orders/:id/simulate-paid` and applies only to `source=local_billing`. |
| **Sandbox** | `ENTITLEMENT_MODE=enforce`, central Entitlement reachable | Web **Client** `/membership`: catalog `providerHint` `wechat` → `wechat_pay_v3`, `alipay` → `alipay_f2f`; may show QR / `codeUrl` / redirect. After pay the page **polls** `GET .../orders/:id` (~2s, ~2 min cap); return or **Complete payment** posts `.../complete`, then refreshes local entitlements. Sandbox secrets live on **Entitlement**, not this repo. **Not** production WeChat / Alipay merchant notify. |
| **Production** | Same mode + production Entitlement / PSP (owner-ops) | VistaRemote lite webhook `POST /api/v1/commerce/webhooks/entitlement` can sync `User.plan`. **WeChat / Alipay platform notify lands on LuminaryWorks Entitlement**, not VistaRemote. Real merchant onboarding, certificates, and platform callbacks are configured in your environment / Entitlement. |

Lite ingress `order.fulfilled` (`POST /api/v1/commerce/webhooks/entitlement`) uses HMAC headers (**FR-BILL-06**) — **not** WeChat / Alipay platform notify verification:

| Header | Requirement |
| :--- | :--- |
| `content-type` | `application/json` |
| `x-lw-timestamp` | Unix seconds (±300s window) |
| `x-lw-nonce` | ≥8 chars; replay protection |
| `x-lw-signature` | `v1=<base64url>` |
| `x-lw-event-id` | Idempotent event id |

Signature: `HMAC-SHA256(ENTITLEMENT_WEBHOOK_SECRET, \`${timestamp}.${nonce}.${rawBody}\`)` → base64url; verify on the **untouched raw body** (never re-serialize JSON). `ENTITLEMENT_WEBHOOK_SECRET` is this ingress HMAC secret and must equal Entitlement `ENTITLEMENT_ORDER_FULFILLED_TARGETS.vistaremote.secret`. Legacy `X-Entitlement-Signature` equality is a **hard-cut 401** with no fallback. Missing secret → **401** (honest reject, not silent mock).

Fulfillment failures (local plan projection write) enter `commerce_webhook_fulfillments` retry; exhausted → dead letter. Admin: `GET/POST /api/v1/admin/commerce-webhook/*` (status / dead-letters / process-once / replay|ignore); audit `commerce.webhook.*` (**FR-BILL-07**).

**Runbook:** WeChat / Alipay **merchant onboarding remains owner-ops** and is not delivered with this repo.

## Webhook user mapping (Logto `sub`)

After signature verification, `order.fulfilled` **`subjectId` must be the Logto OIDC `sub`**. The server resolves the local user via `users.logtoSub` (**not** the local User UUID; users are **never** auto-created).

| User origin | `logtoSub` | Webhook can write `User.plan` |
| :--- | :--- | :--- |
| Web / OIDC login + `POST /api/v1/auth/oidc/exchange` | set | ✓ |
| Admin local register / Controller JWT only | often `null` | ✗ → **400** `WEBHOOK_USER_NOT_FOUND` |

For **local-only users** (no Logto binding), grant plans via:

- Admin **Users** → change plan (Admin plan grant), or
- Order owner commerce **`POST .../complete`** / **`GET .../orders/:id`** (`CommercePlanSyncService.syncForAccessToken` with the caller Bearer token)

Closed-trial paths: Meta-Repo `plan/trial-ops-checklist.md`.

## VistaRemote server env names (names only)

Names below come from `server` source and `server/.env.example`. **Do not invent values.** Keep production secrets in a secret store / Entitlement host — not in git.

This repo has **no** `COMMERCE_*` environment variables. The commerce BFF forwards `/v1/...` using `ENTITLEMENT_BASE_URL`.

| Name | Role |
| :--- | :--- |
| `ENTITLEMENT_MODE` | `off` \| `shadow` \| `enforce` \| `offline_license` |
| `ENTITLEMENT_BASE_URL` | Central Entitlement base URL |
| `ENTITLEMENT_SERVICE_API_KEY` | M2M `X-Service-Key` |
| `ENTITLEMENT_WEBHOOK_SECRET` | Lite ingress HMAC secret (= Entitlement `TARGETS.vistaremote.secret`); empty → webhook **always 401** |
| `COMMERCE_WEBHOOK_POLL_MS` | Fulfillment retry poll interval (default 15000; `<=0` disables) |
| `COMMERCE_WEBHOOK_MAX_ATTEMPTS` | Fulfillment retry cap (default 5 → dead letter) |
| `ENTITLEMENT_CACHE_TTL_MS` | Entitlement cache TTL |
| `ENTITLEMENT_OFFLINE_GRACE_MS` | Offline grace |
| `ENTITLEMENT_DEPLOYMENT_ID` | Deployment id |
| `ENTITLEMENT_LICENSE_PUBLIC_KEYS` | Offline License public-key JSON (`offline_license`) |
| `ENTITLEMENT_LICENSE_PAYLOAD` | Offline License payload (`offline_license`) |
| `ENTITLEMENT_LICENSE_ALLOW_GRACE` | Offline License grace flag |
| `PRODUCT_CODE` | Product code (example: `vistaremote`) |
| `BILLING_ALLOW_SIMULATE_PAID` | Only when `NODE_ENV=production`: `true` re-enables simulate-paid. Production should **omit it or leave it not true** |
| `NODE_ENV` | `production` disables simulate-paid by default |

WeChat / Alipay **merchant ids, APIv3 keys, certificates, and Alipay app secrets** belong on Entitlement / the PSP — **not** VistaRemote server env vars. `ENTITLEMENT_TRIAL_PURGE_*` is trial recording purge, not a payment callback.

## Client Membership (sandbox, not PSP live)

Web **Client** `/membership` (the current viewer Admin has **no** `/membership` route):

1. Accept policies → pick a Pro/Ultra SKU → choose **WeChat Pay** or **Alipay** (catalog `providerHint`, not Entitlement adapter ids).
2. **Checkout** → `POST /api/v1/commerce/orders` then `.../pay`. A QR, payment link, or redirect may appear.
3. The page shows “Waiting for payment confirmation…” and polls order status; **Complete payment** also posts `complete`.
4. When status is `paid` / `fulfilled` / `completed` / `success`, entitlements refresh. The on-page sandbox note is **not** live merchant notify.

Closed trial can also grant via Admin **Users** → change plan, without checkout.

## Checklist

- [ ] **System entitlement flags (FR-WAD-52)**: Admin **System** → entitlement/payment config. `GET /api/v1/admin/system/entitlement` returns only `entitlementMode`, `entitlementBaseUrlConfigured`, and `webhookSecretConfigured`. It must **not** include `ENTITLEMENT_WEBHOOK_SECRET` or a raw base URL. Use **Copy entitlement status JSON** to verify.
- [ ] **Reject a bad signature**: `POST /api/v1/commerce/webhooks/entitlement` with a wrong or missing `x-lw-signature` (or legacy `X-Entitlement-Signature` only) → **401**; local `User.plan` must not change. Unset secret → **401** as well.
- [ ] **Fulfillment dead letters (FR-BILL-07)**: Admin `GET /api/v1/admin/commerce-webhook/dead-letters` lists failures; `process-once` / `replay` / `ignore` available. **WeChat / Alipay merchant onboarding remains owner-ops.**
- [ ] **simulate-paid forbidden for commerce**: Admin **Simulate paid** is shown only on `local_billing` pending rows. `POST /api/v1/admin/orders/:id/simulate-paid` on `source=commerce` returns **400** `COMMERCE_SIMULATE_PAID_FORBIDDEN` (UI: use Membership complete / webhook). Do not call `POST /api/v1/billing/orders/:id/simulate-paid` with an Admin JWT.
- [ ] **Disable simulate-paid in production**: when `NODE_ENV=production` and `BILLING_ALLOW_SIMULATE_PAID` is not `true`, simulate-paid returns **400** `SIMULATE_PAID_DISABLED` (UI: simulate paid disabled in production).
- [ ] **Webhook user mapping**: `subjectId` must be the Entitlement-side Logto `sub` with a matching local `users.logtoSub`; otherwise **400** `WEBHOOK_USER_NOT_FOUND`. Admin-created local users should use plan grant or Client Membership complete/status — **not** webhook auto-grant.
- [ ] **Grant path**: after sandbox Client Membership **pay** + **complete** / **status** polling (or a signed lite webhook when the user is OIDC-bound), the Admin **Users** list shows the matching `plan`. That is a local cache, not proof that production PSP settlement is complete.
- [ ] **No secrets in git**: `.env`, CI logs, and Admin JSON must not contain merchant secrets.

## Not shipped (owner-ops)

Complete these on the **LuminaryWorks Entitlement / PSP consoles**. VistaRemote does **not** accept WeChat / Alipay platform notify; this repo only has lite `POST /api/v1/commerce/webhooks/entitlement`. No production merchant pack ships with VistaRemote:

- WeChat merchant onboarding, APIv3 key and platform certs, payment notify URL **on Entitlement**
- Alipay app and keys, face-to-face / sandbox → production cutover
- Production credentials for PayPal / Wise and other channels
- Store those secrets in the **Entitlement** environment (do not commit them in `server/.env`)

After onboarding, re-run this checklist: entitlement **API** flags, bad-signature 401, and commerce simulate-paid still forbidden.
