# Remote Control (User Guide)

For **operators** using VistaRemote for remote assistance—not developers.

## Roles

| Role | Typical use |
| :--- | :--- |
| **Host (agent)** | Office PC runs Desktop Agent and shows a pairing code |
| **Controller** | Admin enters the code on phone/browser to view and control the desktop |

## How to connect (controller)

| Method | Action |
| :--- | :--- |
| **Numeric code** | Enter 6–8 digits on `/pairing` |
| **QR code** | Scan code shown on host screen |
| **Link** | Open `https://…/join/…` or org short link |

Web routes: `/pairing`, `/join/{token}`.

## Quick steps

### Host (Desktop)

1. Install VistaRemote Agent (Windows / macOS / Linux).
2. Sign in with your organization account (or register the device).
3. Note the **pairing code** on screen (often 6–8 digits, time-limited).
4. Share the code with the controller; **approve** when they connect before screen share starts.

### Controller (Web or Mobile)

1. Open your organization’s VistaRemote URL (browser or app).
2. Enter the pairing code on the pairing page.
3. When status is **connected**, you can see and control the remote desktop.

Technical details: [Pairing](/guide/pairing) (developer-oriented).

## Connection quality

| Issue | Suggestion |
| :--- | :--- |
| Laggy video | Check network on both sides; IT may provide TURN |
| LAN only | Ask IT to allow UDP or deploy TURN |
| Multiple viewers | Requires **Pro/Enterprise** (SFU); may be limited after trial |

## Multiple displays (Web controller)

When the host has two or more monitors:

| Action | Behavior |
| :--- | :--- |
| Toolbar switch | Single-stream: switch which remote display you view/control |
| **Multi-window** | Up to **2** parallel streams (split pane or pop-out); each pane controls its own display |
| Exit multi-window | Back to one stream; toolbar switching still works |
| 3+ monitors | P2P shows only 2 streams; use switch or later SFU for the rest |

## Host Agent

- Closing the window keeps the Agent in the **system tray**; restore, disconnect, or quit from the tray.
- Tray menu includes **Open at login**.
- **Linux**: X11 / XWayland inject directly; pure Wayland needs Screen sharing + Remote Desktop portal consent. See [Linux remote control](/guide/linux-remote-control).

## Clipboard, files, terminal, chat, processes, services, power, and host (Web / Viewer)

After the session is connected and the host has armed control, the side panel can:

- Sync **plain-text** clipboard both ways (host copies update the viewer)
- List the host user home directory, upload/download, create folders, delete, **rename**, and **copy** (inside the jail; copy is files only)
- Open an **xterm** user-session terminal (Windows ConPTY / POSIX PTY; for example `echo` / `dir` / `tput cols`)
- Chat with the person at the host
- List processes and end a task (not pid 1 or the Agent itself)
- **Read-only** list of system services (no remote start/stop)
- **Reboot / shut down** after a typed confirmation; the action is delayed several seconds
- Read **host info** (name / OS / IP), send a desktop notification, and **lock the screen** (confirmation required)
- Open an **http/https** URL in the host’s default browser (`file:` / `javascript:` are rejected)
- Toolbar **Screenshot**: save the current frame as a PNG on the controller (not via the server)

Accounts without the matching permission do not see the terminal, services, power, or host tabs. VistaRemote does not include Intel AMT, remote printing, registry editing, Wake-on-LAN magic packets, service start/stop, or Windows Update.

The host must **Allow** in the Agent window before keyboard, mouse, and ops channels work; **View only** keeps the video. The host desktop shows an always-on-top **connection bar** to disconnect. Inject and ops channels stop as soon as the session disconnects.

## Manual acceptance checklist (one pass)

Run this on a **logged-in** Agent plus the Web controller. **Sign out and sign in again** first so the controller JWT includes ops permissions. For power and lock on a development machine, set `VISTAREMOTE_POWER_DRY_RUN=1` and `VISTAREMOTE_HOST_DRY_RUN=1` so the host is not actually rebooted or locked.

| # | Step | Expected |
| :--- | :--- | :--- |
| 1 | Host shows a pairing code; controller joins via `/pairing` | Video appears; status connected |
| 2 | Host has not clicked Allow | Mouse/keyboard do nothing; ops ignored |
| 3 | Host clicks Allow | Input works; side tabs appear |
| 4 | Connection bar Disconnect | Inject stops immediately |
| 5 | Clipboard: send text / copy on host | Plain text both ways |
| 6 | Files: list, upload, download, mkdir, delete, rename, copy | All inside the home jail; `..` cannot escape |
| 7 | Terminal: open xterm, run `echo`; enlarge the pane | Output; column count changes (`tput cols`) |
| 8 | Chat both ways | Visible on both; server audit has no body |
| 9 | Process list; end a test process you started | List refreshes; Agent cannot be killed |
| 10 | Services tab | Read-only list; no start/stop |
| 11 | Power (dry-run or real host) | Rejected without confirm; scheduled after confirm |
| 12 | Host: sysinfo, notify, lock (dry-run or real host) | Info visible; host shows a notification |
| 13 | Open `https://example.com`; try `file://` | First opens in the host browser; second errors |
| 14 | Toolbar Screenshot | PNG downloads locally |
| 15 | Pairing page: check **View only**, then join | No terminal / services / power / host tabs; no mouse/keyboard channel |

**Out of scope (do not test):** Intel AMT / IP-KVM, Mesh JPEG, remote printing, registry, service start/stop, Wake-on-LAN, UAC/logon desktop, file clipboard, USB, audio mix.

## Security

- Do not share pairing codes with untrusted parties; codes expire and are **one-shot** (`PAIRING_CONSUMED`) — a class cannot reuse one code.
- End the session and stop sharing when finished.
- Enterprise editions may enable audit and behavior policies (admin-configured).
