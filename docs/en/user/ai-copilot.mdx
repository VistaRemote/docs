# AI assist and local MCP (Windows / macOS)

AI assist is off unless you turn it on. After that there are two paths. Both only act on a **session that is already allowed**:

1. **Viewer**: type a task in the AI assist drawer so your organization's AI Worker clicks and types in windows already open on the remote Windows or macOS Agent, including the browser.
2. **Local MCP (Cursor / ChatGPT)**: call `vr_*` tools on that same allowed session from your machine. It **cannot** open a new remote session.

The tool surface matches open-source **[Windows-MCP](https://github.com/CursorTouch/Windows-MCP)** and **MacOS-MCP**-style look → click/type. VistaRemote does **not** bundle those programs. By default it maps the same allowed steps onto the existing WebRTC DataChannel. An optional Agent setting (`VR_COPILOT_BACKEND=platform-mcp`) can start `windows-mcp` or `macos-mcp` on local stdio and, if that process fails, falls back to the same input path.

This is not unattended takeover. It does not run scripts, edit the registry, or write files.

## Why this is a core capability

| | VistaRemote AI assist / local MCP | Typical desktop MCP (Windows-MCP / MacOS-MCP) |
| :--- | :--- | :--- |
| Target | Remote Windows / macOS Agent | Local desktop |
| Tools | Snapshot, Click, Type, scroll — bounded | Same look → click/type |
| Transport | Live remote session (Viewer or local MCP) | Local MCP host |
| Consent | Second "Allow AI" after remote control | Trust the host |
| Default | Off; alerts never auto-start control | Up to the host |

Use it to help a colleague open a settings page, fill a form in their browser, or walk through troubleshooting — not to run scripts or edit the registry from Viewer.

## Before you start

1. The remote PC already has the Agent (Windows or macOS), and you are in the same session.
2. The host taps Allow for remote control (keyboard and mouse only).
3. If that Agent has AI assist on (`VR_COPILOT=on`), the host sees a second prompt. After **Allow AI**, the Viewer toolbar shows **AI assist**, and local MCP `vr_*` tools can run. Without that, AI never injects input.
4. On the Viewer path, one still frame goes to your own AI service. This feature does not require a public model by default.

## Viewer

1. Open **AI assist** from the Viewer toolbar. Human chat stays on its own button.
2. Write the task, for example "click the browser address bar". An empty task does not start.
3. The step list shows tool names such as Click or Type.
4. Press **Stop**, or move the mouse or keyboard yourself. The AI pauses. Your own control works as before.

One task stops after about 20 steps or 3 minutes.

## Local AI (Cursor / ChatGPT)

A local MCP process can operate a session you have **already joined**, after the remote host has allowed AI. It cannot open a new remote session. If the server flag is off, the tools return `COPILOT_DISABLED`. If AI is not armed, they return `COPILOT_NOT_ARMED` and inject nothing.

Use the same command for ChatGPT desktop when it can launch a local stdio MCP. Do not put a real ticket in git. The example is `tooling/mcp/cursor-mcp.example.json`:

```json
{
  "mcpServers": {
    "vista-remote": {
      "command": "node",
      "args": [
        "tooling/mcp/vista-remote-mcp.mjs"
      ],
      "env": {
        "VR_API_URL": "http://127.0.0.1:3000",
        "VR_SIGNALING_TICKET": "<signaling-ticket-for-an-existing-session>",
        "VR_SESSION_ID": "<session-id>"
      }
    }
  }
}
```

Tools are `vr_snapshot`, `vr_click`, `vr_type`, `vr_scroll`, `vr_move`, `vr_shortcut`, and `vr_wait`. PowerShell, shell, and the ecosystem `remote_control` handoff tool are not in this list.

## Not in this version

- Whether a click lands on a real Windows or macOS desktop still needs a person to look. This page does not call the feature production-signed.
- It does not lock the screen, sign out, run PowerShell or a shell, or edit the registry.
- An alert does not start a remote session or this assist by itself.
- The same AI action is not broadcast to a group of computers.
