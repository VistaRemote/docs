# Releases

VistaRemote uses **per-repository builds and releases**: each sub-repo has its own SemVer tags and GitHub Actions workflows. When `@vistaremote/shared` is published, downstream repos are notified to bump their dependency.

> Full normative spec: Meta-Repo [spec/cicd-release-spec.md](https://github.com/VistaRemote/vista-remote/blob/main/spec/cicd-release-spec.md)

## Tag conventions

Each repository uses its own prefix plus a semantic version. The **tag** is the release. Keep `package.json` aligned with that tag.

| Repo | Tag prefix | Artifact |
| :--- | :--- | :--- |
| **shared** | `v` | npm `@vistaremote/shared` (GitHub Packages) |
| **server** | `server-v` | Docker `ghcr.io/vistaremote/server` |
| **ai** | `ai-v` | Docker `ghcr.io/vistaremote/ai` |
| **web** | `web-v` | Static artifacts (client + admin) |
| **desktop** | `desktop-v` | Windows / macOS installers |
| **docs** | `docs-v` | GitHub Pages |
| **deploy** | `deploy-v` | Compose validation / release notes |
| **mobile** | `mobile-v` | Android package |
| **downloads** (public) | `v` | Windows Agent + Android APK (anonymous download) |

**Tags are the source of truth** for releases; keep `package.json#version` aligned when possible.

## End-user installers (public bucket)

`desktop` / `mobile` source may stay **private**. User-facing binaries are published to the public repo **[VistaRemote/downloads](https://github.com/VistaRemote/downloads)**. The marketing site `/download` page defaults to that repo’s `releases/latest/download`.

From the Meta-Repo:

```bash
pnpm pack:publish          # pack:all + upload to VistaRemote/downloads Release
pnpm publish:downloads     # upload existing artifacts only
```

Requires `gh auth login` and matching `desktop` / `mobile` package versions. Prefer building the Windows Agent on Windows or via the `desktop` Actions workflow (`windows-latest`); Android APK can be built on macOS with `pnpm pack:mobile`.

Website defaults:

- `NEXT_PUBLIC_RELEASE_BASE=https://github.com/VistaRemote/downloads/releases/latest/download`
- `NEXT_PUBLIC_RELEASE_VERSION` matches the release id in the asset filenames

## Recommended release order

1. Merge `shared` to `main`.
2. Tag `shared` with the `v` prefix and push it. `release.yml` publishes the npm package.
3. `repository_dispatch` makes each consumer `sync-shared.yml` open a dependency PR.
4. After those PRs merge, tag `server`, `web`, and the other repos with their own prefixes.
5. Point Compose image tags at the new releases, then tag `deploy`.

### Publish shared

In the `shared` repo, align `package.json` with the tag you are about to push, then push that tag to `origin`.

Workflow `shared/.github/workflows/release.yml`: lint → test → build → publish → notify `server` / `web` / `ai` / `desktop` / `mobile`.

### Consumer auto-bump

`sync-shared.yml` on each consumer:

- Moves `@vistaremote/shared` to the version just published
- Runs install, lint, test, and build
- Opens a dependency bump PR

Review and merge it.

### Release a service

In that repo (for example `server`), push a tag that uses the repo prefix. Its `release.yml` publishes the image or static assets.

## Local vs CI vs production

| Environment | `@vistaremote/shared` |
| :--- | :--- |
| **Meta-Repo dev** | `file:../shared` in `package.json` |
| **GitHub Actions** | `setup-shared` composite action (sibling checkout) |
| **Docker / offline** | GitHub Packages pinned SemVer |

Restore local `file:` deps after a registry bump:

```bash
node tooling/scripts/restore-shared-file-deps.mjs
```

## CI workflows

| Workflow | Trigger | Purpose |
| :--- | :--- | :--- |
| `ci.yml` | push / PR | setup-shared → lint → test → build |
| `sync-shared.yml` | `shared-published` | Auto bump + PR |
| `release.yml` | tag | Images / static site / npm |
| `dependency-review.yml` | PR | Dependency review |
| CodeQL | push / PR | Security analysis |

Meta-Repo `meta-ci.yml` only checks scaffolding, not sub-repo app code.

## Maintainer setup

Secret on **`VistaRemote/shared`**: `VISTAREMOTE_CI_PAT` (`repo` + `workflow`) for cross-repo dispatch.

Sync workflow templates from Meta-Repo root:

```bash
node tooling/scripts/setup-github-workflows.mjs
```
