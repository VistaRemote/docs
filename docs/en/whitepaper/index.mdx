## Summary

VistaRemote is a **cross-platform remote desktop** in the VibeCode ecosystem. **WebRTC** is the transport: **one-to-one** sessions prefer a **direct P2P** path, and **one-to-many viewing** switches to an **SFU** so the host uploads once. Control input uses an **SCTP DataChannel**, separate from audio and video.

The engineering model is a **flat meta-repo**: TypeScript across the stack, with Electron and React Native isolated from each other. The relational database is **PostgreSQL 16**. Product behavior is written as Specs before code, so people and AI collaborators change the same contract.

Compared with traditional desktop monitoring, VistaRemote is **live remote control**, not only a recording after the fact. You can **host it yourself**, and AI analysis can stay on your network. See [Positioning](/architecture/positioning).

## 1. The problem

Remote desktop is basic infrastructure for IT support, customer help, remote work, and training. Older products share a few limits:

- **Latency** from TCP or proprietary protocols, especially across firewalls.
- **Lock-in** to a vendor relay, with cost and data-sovereignty consequences.
- **Old stacks**, often a C/C++ monolith that is expensive to extend to the web and to phones.
- **Privacy**: picture and input pass through a third-party cloud.

WebRTC is mature in browsers and native apps. Codecs, DTLS-SRTP, ICE, and DataChannel make **“control a desktop from a browser”** a normal product. VistaRemote treats WebRTC as a first-class path and uses TypeScript for signaling, clients, and contracts.

## 2. What it is

> **High-performance, self-hosted, auditable remote desktop as a normal part of a modern web stack.**

| | |
| :--- | :--- |
| **Who it is for** | Developers, SMB IT, support teams, and the VibeCode community |
| **How it is deployed** | Private / self-hosted, or hosted for you |
| **What is different** | Live WebRTC remote control, private AI, and an open TypeScript stack on PostgreSQL |
| **What it is not** | A heavy VDI, game-grade frame sync, or silent monitoring without consent |

1. **WebRTC** for low-latency control and viewing (P2P / SFU), rather than a proprietary screen recorder.
2. **AI you control**: a separate `ai` service. Run **Ollama** yourself so recordings and insight stay inside.
3. **Auditable code** versus closed desktop-monitoring suites. Data sovereignty stays with the organization.
4. **TypeScript** so hiring, customization, and Docker deployment stay inexpensive.

## 4. Architecture

The server does **not** forward media. It does signaling, authorization, ICE configuration, and SFU scheduling.

| Path | Technology |
| :--- | :--- |
| Video / audio | RTP over DTLS-SRTP |
| Control | SCTP DataChannel |
| Signaling | WebSocket + JSON |

| Viewers | Strategy | Why |
| :--- | :--- | :--- |
| 1:1 | **P2P** | Lowest latency, no SFU bandwidth |
| 1:N | **SFU** | The host does not upload N copies |

Details: [WebRTC topology](/architecture/webrtc-topology) · [Development](/architecture/webrtc-development) · [Messaging](/architecture/messaging-transport) · [Overview](/architecture/overview).

| `desktop` | Electron Agent |
| `web` | Browser controller |

## 5. Security

| Principle | How |
| :--- | :--- |
| Least privilege | The host explicitly allows the session; capture and input stop when it ends |
| Transport | WSS for signaling; DTLS-SRTP for media |
| Self-host | Signaling, TURN, and SFU can run in the customer’s domain |
| Audit | Connect, disconnect, and identity logs on the server |
| Secrets | Environment variables and short-lived TURN credentials, not hardcoded clients |

| Layer | Choice |
| :--- | :--- |

| Objects | MinIO / S3 for recordings |

| Desktop | Electron |
| Mobile | React Native |
| Realtime | WebRTC (P2P / SFU) and coturn-compatible TURN |

## 10. Risks and responses

| Risk | Response |
| :--- | :--- |
| NAT failure | Configurable TURN; documented firewall ports |
| Poor quality on a weak network | Simulcast / SVC and dynamic resolution |
| Clients drift apart | `shared` as the only contract, changed first |
| Electron and React Native build conflicts | Separate repos |
| Misuse | Consent UI, audit logs, no silent monitoring |
| AI privacy | Plan entitlements, PII handling, optional private LLM (Ollama) |
| AI load on signaling | Separate `ai` service and an async queue |
