## 1. Project Background (项目背景)

In the modern enterprise IT ecosystem and the broader remote-collaboration landscape, remote desktop control systems serve as critical infrastructure. However, traditional commercial solutions frequently present significant limitations:
*   **High Latency & Proprietary Protocols**: Many systems rely on TCP-based or non-optimized streaming protocols, leading to unacceptable lag across strict firewalls or international networks.
*   **Monolithic Tech Stacks**: Existing open-source alternatives often utilize monolithic C/C++ bases, raising the barrier to entry for modern web/mobile full-stack developers and slowing feature iteration.
*   **Security & Privacy Vulnerabilities**: Centralized cloud-relay systems risk leaking sensitive enterprise telemetry and control vectors.

### The VibeCode Vision
As a flagship open-source initiative under **VibeCode**, **VistaRemote** was conceived to build a high-performance, cross-platform, enterprise-grade remote desktop system. By capitalizing on **WebRTC (P2P / SFU hybrid topology)**, VistaRemote delivers near-zero latency video streaming and seamless remote orchestration directly inside browsers, native desktop clients, and mobile devices.

### Core Differentiators (核心优势)

Compared with **traditional screen-recording monitoring** and **closed-source enterprise DLP/desktop surveillance**:

| Pillar | VistaRemote |
| :--- | :--- |
| **WebRTC-native** | Real-time remote control and streaming—not legacy TCP DVR-style monitoring only |
| **Open source & self-hosted** | Full stack on-prem: **MySQL**, MinIO, optional **private LLM (Ollama)**—AI data stays inside the enterprise |
| **TypeScript end-to-end** | Lower hiring friction in China, lower customization cost, Spec-Driven + Vibe Code |
| **AI by design** | Dedicated `ai` workers; not bolted onto a proprietary cloud |

Detailed positioning (including **why MySQL over PostgreSQL** for domestic teams): [产品定位](/architecture/positioning).

## 2. System Architecture Selection (工程目录架构演进)

A primary architectural challenge for VistaRemote was code organization. Given that our entire tech stack relies on TypeScript/JavaScript (NestJS, React, React Native, Electron), standard practice suggests a Monorepo via Turborepo or Nx.

However, after deeply analyzing our cross-platform build pipelines, we rejected the Monorepo architecture in favor of a **Flat Meta-Repo Model**.

### 2.1 Monorepo vs. Multi-Repo Structural Comparison

| Dimension | Monorepo (Turborepo) | Multi-Repo (Our Meta-Repo Selection) |
| :--- | :--- | :--- |
| **Native Module Isolation** | ❌ **High Risk**. Shared `node_modules` causes dependency hoisting conflicts between Electron (C++ native addons) and React Native (Metro/Gradle). | ✅ **Perfect Isolation**. Every runtime environment has its own independent, sandboxed package root. |
| **Build Pipelines** | ⚠️ **Heavyweight**. Combining NestJS (`tsc`), Rsbuild (`Rspack`), and Native Mobile build chains throttles local dev efficiency. | ✅ **Decoupled**. Fast independent compilation using Rust-powered tooling (`Rsbuild`, `Rspress`) and standard runtime engines. |
| **Data Contract Sync** | ✅ **Seamless**. Direct workspace package imports. | ⚠️ **Requires Orchestration**. Addressed elegantly via a centralized physical `shared` workspace protocol. |

### 2.2 Why Turborepo Fails for VistaRemote's Native Layers
1.  **The Electron C++ Build Trap**: The desktop agent utilizes native low-level OS hook modules (e.g., `@nut-tree/nut-js` or `robotjs`) compiled via `node-gyp`. Hoisting these packages in a Monorepo workspace heavily corrupts platform-specific path resolution.
2.  **The React Native Metro Symlink Conflict**: The React Native Metro bundler notoriously struggles with symbolic links generated by Monorepo workspace topologies.
3.  **Modernizing with Rspack**: We have standardized our Web environment around the cutting-edge Rust-based **Rsbuild** and **Rspress** stack. Forcing these high-velocity tools into an omnibus configuration alongside legacy mobile/backend bundles induces unnecessary maintainer friction.

## 3. The VistaRemote Meta-Repo Framework

To circumvent Multi-Repo desynchronization while preserving compilation safety, VistaRemote employs a **Meta-Repo layout**:

```text
vistaRemote/ (Meta-Repo Root)
├── init.sh                  # Distributed repository orchestrator
├── spec/                    # System design blueprints and compliance bounds
├── shared/                  # THE SINGLE SOURCE OF TRUTH (TypeScript Types & Contracts)
├── server/                  # NestJS + TypeORM + MySQL
├── ai/                      # AI/分析 Worker（BullMQ + LLM，独立仓库）
├── web/                     # Rsbuild: apps/client + apps/admin (全用户管理台)
├── desktop/                 # Controlled Agent & Dashboard (Electron + React)
├── mobile/                  # Native mobile app controller (React Native)
└── docs/                    # Technical documentation engine (Rspress + MDX)
```

### WebRTC topology (normative summary)

| Scenario | Topology |
| :--- | :--- |
| 1 controller : 1 agent | **P2P** (STUN/TURN as needed) |
| 1 agent : N controllers (view-only / broadcast) | **SFU** (single uplink from agent) |

Media never terminates in the NestJS process; the server handles signaling, auth, ICE config, and SFU scheduling only. Requirement IDs are defined in Meta-Repo `spec/system-overview.md`.
